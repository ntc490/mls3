# PDF Import Plan

Replace the copy-and-paste TSV import with an in-app import that reads the two PDF
reports printed from the church website. The existing paste-based flow depends on
which browser produced the text; the PDFs do not.

Status: **implemented.** See "What was built" at the end for where things live and
what changed from this plan.

## Goals

- Import members and households from two printed PDFs, from the phone, in the app.
- Never lose MLS3-specific data (prayer history, `dont_ask_prayer`, notes, flags,
  `aka`, `skip_until`).
- Back up everything before writing, and make restore a single tap.
- Confirm before committing. No per-record review — the preview shows counts plus
  exceptions only.
- Members absent from the new import are deactivated, not deleted.

## The two reports

Both are generated by WeasyPrint 60.1 and titled "Member List". They are
distinguishable by their columns: the household report has a `Household Members`
column, the member list does not. The import page uses that to work out which
uploaded file is which, so the user does not have to match files to slots.

### Member list

Columns are whatever was selected when printing. Required: `Name`, `Gender`,
`Birth Date`. Used when present: `Phone Number`. Parsed but ignored: `Address`,
`Email`. `Age` is read when present and used only as a consistency check against
the age computed from `Birth Date`.

`Name` is `Last, First [Middle]`. `Birth Date` is `5 Dec 1953`.

The last page prints `Count: N`. The parser checks its record count against it and
refuses the import on mismatch.

### Household report

Nested table. Column 1 holds the household name (`Anderson, Bryan & Barbara`),
then phone, then 0-3 address lines. Column 2 lists that household's people, with
`Gender` and `Age` beside them.

**Column 2 is indented at two levels, and the indent is the parent/child marker:**
heads of household sit at the outer level, dependents at the inner one. This is
authoritative and replaces every heuristic considered earlier — see "Why not infer
households from the address" below.

A person is written as a bare first name (inherit the household's surname) or as
`Surname, First [Middle]` when their surname differs (`Savage, Landon Scott`).
Surname case may differ between the household name and the member entry
(`DeAngelis, Travis Don & Dani` contains `Deangelis, Dani`), so joins are
case-insensitive.

`Age` is printed only for minors.

## Parsing approach

`pdftotext -layout` is unusable here: cells wrap to several lines and its line
grouping fuses adjacent columns (a birth date merges with the second line of an
address). Everything below is coordinate-based instead.

### Row boundaries come from the PDF's own table rectangles

Each page's content stream draws the table's cell rectangles — a group of
rectangles sharing one `y` and `height` is one table row. Decompress the stream
with `zlib` and collect them.

Rows are **zebra-striped**: only every other row is drawn. Rows are contiguous, so
an undrawn row is exactly the gap between two drawn ones and is recovered by
filling gaps. A white row at the very top or bottom of a page draws nothing and has
no neighbouring gap, so those are recovered from any text that falls outside all
bands but inside the table region.

Coordinates in the content stream are scaled by 0.75 relative to `pdftotext`
output, and the page footer must be located before the trailing-row fill or the
last row of most pages is lost.

### Columns come from the report, never hardcoded

Take the cell rectangles of the **header row**, discard the full-width row
background (the cell that contains all the others), and the remainder are the exact
column spans. Label each span by which header words fall inside it; this handles
multi-word headers (`Birth Date`) and headers that wrap onto two lines
(`Phone` over `Number` in the with-address layout, side by side in the
without-address one).

This is what lets one parser read both column layouts. Hardcoded x-positions would
break the moment a column is added or removed.

### Joining words within a cell

Group a cell's words into lines by `y`, then join lines:

- `email`: concatenate with no separator — emails wrap mid-token
  (`Barbara.anderson111@comcast.ne` + `t`).
- everything else: join with a space, except when the previous line ends in `-`,
  which joins with no space (`Joe-` + `Courage` → `Joe-Courage`).

### Rows that straddle a page break

A row's cells can land on different pages: the name on page N and the address on
page N+1, or the reverse. Thirteen rows do this in the with-address sample.

The rule, and the direction matters:

- a fragment with no name at a page's **bottom** merges **forward** into the next
  page's first row;
- a fragment with no name at a page's **top** merges **backward** into the previous
  page's last row.

Getting this backwards silently fuses two adjacent people into one record with
doubled fields and raises no error. It needs a test (see "Tests").

### Household report specifics

Row clustering needs a **~5pt y-tolerance**: the household name line sits about 3pt
above its first member line, so an exact-`y` grouping splits them and misassigns
every household's first person to the previous household.

Within the member column, the indent level must be taken from the **first word of
the line**, not per word — a two-word head-level name (`Samantha Charlene`) has its
second word past the dependent indent and would otherwise be counted as an extra
dependent.

A household block begins at a column-1 line matching `^[A-Z][A-Za-z.'\- ]*,\s` that
does not start with a digit; subsequent column-1 lines are the phone (if it matches
a phone pattern and none is set yet) then address lines. Households straddle page
breaks without special handling as long as the "current household" is not reset per
page.

## Why not infer households from the address

The first plan derived households by grouping the member list on a normalised
street line, because the household report had not been looked at yet. Both of its
core inferences are wrong on the real data:

- **18 addresses host more than one household** — `12087 S Janice Dr` holds
  Damiano, Payne (Caleb), and Payne (Taylor); `3357 W Law Creek Cir` holds
  `Butterfield, Chad` and `Butterfield, Chad & Debbie`. Address grouping produced
  106 groups where there are 145 households.
- **44 dependents are adults** — grown children still at home (33, 32, 31, 29, 26…).
  Any age-based parent test promotes several of them to parent. The household
  report's indentation gets all 44 right.

Address-based inference is dropped entirely. No heuristics, no confidence scores,
no ambiguity queue.

## Data model changes

Add one field to `Member`:

```python
household_role: str = ""   # 'head' | 'dependent' | ''
```

`MemberDatabase.get_parents()` (models.py:447) currently resolves parents *only* by
string-parsing `household.name` through `_parse_parent_names()` (models.py:494).
That works today but is fragile — it breaks when a head's surname differs from the
household name, and it cannot tell a 26-year-old dependent from a parent. Rewrite
it to return the household's `household_role == 'head'` members, keeping the
name-parsing path as a fallback for rows imported before this change.

`Household.email` has no source in the household report: preserve the existing
value on update, leave empty for new households.

No email field is added to `Member`. Email is parsed and discarded.

### Dependency choice

**poppler (`pdftotext -bbox`) for text, `zlib` for the row rectangles.**

Text extraction uses `pdftotext -bbox`, which gives every word with a bounding box.
Row rectangles come from the page content stream, decompressed with `zlib` from the
standard library — `pdftotext` reports text but not vector graphics, so this part is
needed regardless of which text extractor is used. It is about 20 lines of regex
over the decompressed stream.

Termux requires `pkg install poppler`. This is not a new kind of dependency for this
app: `start.sh:105` already hard-fails without `termux-open-url` and directs the user
to `pkg install termux-api`, `utils/version.py:37` shells out to `git`, and SMS
delivery goes through Tasker, a separate Android app.

Two alternatives were considered and rejected:

- *Hand-rolled text extraction* (content-stream tokenizing plus `ToUnicode` CMap
  decoding, ~200 lines). Avoids the package install, but it is the most bug-prone
  part of the feature and the most likely to meet a font encoding it does not
  handle. Not worth owning to avoid one `pkg install`.
- *`pdfplumber`*. Would shrink the parser to roughly 60 lines, but pulls
  `pdfminer.six` → `cryptography`, which on Termux is a system package anyway — the
  same install cost with a larger surface.

Add a preflight check for `pdftotext` so a missing binary produces a clear message
rather than a stack trace, matching how `start.sh` checks for `termux-api`. Document
the install in `docs/DEPLOYMENT.md`.

## Backups

`create_backup()` (utils/import_members.py:538) only copies `members.csv`. An
import rewrites members *and* households, and reassigning household IDs can orphan
references, so snapshot the whole dataset:

```
data/backups/<YYYYMMDD_HHMMSS>/
    members.csv
    households.csv
    prayer_assignments.csv
    appointments.csv
    manifest.json     # timestamp, app version, source PDF filenames, record counts
```

- Taken before any write, every time, not optional.
- `restore(timestamp)` copies the set back, taking its own safety snapshot first.
- Retain the last N (10) snapshots; prune oldest beyond that.
- `data/backups/` is already gitignored.

## Import flow

```
/import
  ├─ two file pickers; app identifies which report is which
  ├─ refuses two files of the same kind, with a clear message
  └─ Continue enabled only when both parse

POST /api/import/preview          — parse + cross-validate + diff. Writes nothing.
POST /api/import/commit           — backup, then merge. Returns the backup id.
POST /api/import/restore          — roll back to a chosen snapshot.
```

### Cross-validation, before any preview is shown

1. Each report's record count matches its own printed `Count:`.
2. The two reports have the same number of people.
3. Every household member joins to a member-list record, and vice versa.
4. Genders agree; ages agree where the household report prints one.
5. Footer print dates match (both samples: `12 Sep 2026`). A mismatch is the
   easiest mistake to make and is flagged, not silently accepted.

Any failure blocks the import and says what is wrong — including a missing required
column ("this report doesn't include Birth Date; turn that column on when
printing").

### Preview

No per-record review; it is unusable on a phone. Headline counts plus exceptions
only, each expandable:

```
342 people · 145 households

  +4  new
  ~11 updated          (old → new, per field)
  −3  deactivated
  325 unchanged

  ⚠ 1 surname spelling changed (Deangelis → DeAngelis)
```

A typical import is a dozen lines. Full detail stays one tap away.

### Confirm and commit

"This will change N records. A backup will be saved first. Import?" → commit →
result page showing the backup id and a Restore button.

Commit uses the existing `merge_members()` (utils/import_members.py:173) with
`activate_present=True, deactivate_absent=True`, then links households in the same
operation:

- **Absent members are deactivated**, never deleted. Their record, prayer history,
  notes and flags are kept intact.
- **Returning members are reactivated** automatically on a later import.
- No UI change is needed for this: `templates/members_list.html:16` already
  defaults the members page to `Active: Yes`, so deactivated people leave the
  default view and stay reachable through the filter.

### Household identity across imports

`household_id` must stay stable or every `member.household_id` reference churns.
Household names are not stable — `Butterfield, Chad` becomes
`Butterfield, Chad & Debbie` when a spouse is added. Match existing households in
this order:

1. by the set of head members (most stable);
2. failing that, by household name;
3. failing that, treat as new and allocate a fresh id.

## Tests

The parser needs fixtures, using the three sample reports plus the household
report. Priority cases, each of which broke a prototype:

- Page-straddle stitch direction — a bottom-of-page fragment merging backwards
  fuses two people into one record and raises no error.
- Column detection on both layouts (with and without `Address`).
- Household row clustering tolerance — an exact-`y` match misassigns the first
  person of every household.
- Head-level indent taken from the line, not the word — `Samantha Charlene` becomes
  a phantom dependent otherwise.
- Wrapped email rejoin and trailing-hyphen name rejoin.
- `Count:` mismatch aborts the import.
- A household whose head has a different surname (`Campbell, Brayden & Hunter`
  containing `Glad, Hunter`).
- The addressless household (`Barton, Linda`) and the nine phoneless ones.

## What was built

Everything above, with these deviations worth knowing about.

**Preview and commit share one code path.** `ImportPlan` is computed by
`build_plan()` and applied by `commit()`, so the confirmation screen shows exactly
what will be written. `merge_members()` in `utils/import_members.py` is untouched
and still serves the CLI/TSV path.

**`build_plan()` reports problems rather than raising.** Parse and cross-check
failures land in `plan.errors` so the page can show them; `commit()` refuses a plan
that carries any error.

**Renames are detected and applied as updates.** A corrected spelling would
otherwise read as one arrival plus one departure, stranding that person's prayer
history on a deactivated row. A match on birth date plus gender, unambiguous in
both directions, is treated as the same person. Case-only changes never reach this
path, because names are matched case-insensitively to begin with.

**Households that predate an import are left in place.** They are not deleted even
when every member has moved on, because deactivated members still point at them.
The stored household count is therefore >= the report's.

**Indent levels are derived, not fixed.** The two levels in the household report
sit only ~15pt apart inside a ~133pt column, so a fraction-of-column threshold puts
everyone at head level. The split is computed from the indents the report actually
uses.

**`*.pdf` is gitignored.** The sample reports hold 342 real names, birth dates,
phone numbers and addresses.

### One finding worth recording

Rewriting `get_parents()` to use `household_role` produces **identical parent lists
to the old name-parsing method for all 61 minors in the sample ward**. The change
is not fixing a live bug for minors; it removes a class of fragility (a head whose
surname differs from the household name, and the age-18 stand-in for parenthood)
and makes the relationship explicit in the data. The genuinely new information is
the 44 adult dependents, which no age test could have identified.
